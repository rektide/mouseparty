# Mouse Party reuse boundaries and platform compatibility

**Recommendation:** Start with the Go activity package and a single guest app such as Polls, not the whole guest page or the Wails desktop binary. The rules already run without the desktop shell; the individual guest modules have a small mounting contract. If the goal is compatibility with existing guest pages, preserve the keyed HTTP/WebSocket protocol and its behavior instead. A Linux desktop build, browser interoperability, and Linux sandbox parity are three different claims.

**Scope:** `~/src/mouseparty-rune`, code at `815c2d53d56367e4f91134758f9e5572d4a67390` (content tip `81baddc1b6e2a208c6b4827576e235d6d146063d`). Source inspection plus isolated `./apps` test runs below; the root Linux build probe is separate. No implementation or video pipeline evaluation.

## Two frontends, two contracts

| Surface | Current boundary | Reuse implications |
| --- | --- | --- |
| **Host control window** | `web/window/` → `frontend/`; Wails serves the embedded files and binds Go `App` as `window.go.main.App`. The manually maintained [`wails.d.ts`](../../web/window/wails.d.ts) defines promise calls, `View`, event subscriptions (`view`, `ask`, `edit`), file drop and clipboard. [`App.run`/`publish`](../../app.go) serialize state changes and push changed snapshots. | The DOM, CSS, queue and settings screens can run in a regular browser **with a bridge**. Match commands, promise results, event order and initial `GetView`, not just file names. Native drops deliver *local file paths* with coordinates; an ordinary browser's `File` objects do not provide the same contract. `LinkClicked` also performs host clipboard work in Go. [`browser_test.go`](../../browser_test.go) proves there is a bridge seam, but its reflection-based HTTP RPC and `GetView` polling are test fixtures, not a production API or proof of Wails behavior. Never expose that privileged interface on the guest origin. |
| **Guest page** | `web/viewer/` → `host_web/`; despite its name, `host_web/host.js` is the guest's script. [`viewer.html`](../../host_web/viewer.html) gets `window.MOUSEPARTY_BASE` from the server's `{{KEY}}` substitution. [`web.go`](../../web.go) serves same-origin keyed assets, `/status`, `/ws`, app modules and document/Office/picture routes; it prefers `../Resources/host_web` if present, then falls back to embedded assets. [`host.ts`](../../web/viewer/host.ts) handles chat, app lifecycles and layouts, and also owns integrations outside the social layer. | No Wails, browser Go runtime or native client install for guests. But the page is not a static standalone site or a drop-in widget: it expects the keyed routes, the viewer DOM/CSS, and the JSON protocol. Keep classic `host.js`, the app modules and worker URLs/MIME types working; test an actual module fetch (including relative imports), not merely the initial HTML. |
| **Individual guest apps** | [`types.ts`](../../web/viewer/types.ts) defines `Start(ctx, view)` plus optional `view`, `message`, `said`, `resize` and `stop` callbacks. `Ctx` supplies the mount element, send/open/close, viewer identity, geometry, keyed base URL and current position/page. [`host.ts`](../../web/viewer/host.ts) lazy-loads `apps/<script>.js`, and [`lib.ts`](../../web/viewer/apps/lib.ts) supplies shared DOM helpers. | Mount one module in a small browser fixture with a synthetic context and matching styles. Begin with Polls or a self-contained word game. Do not infer that all modules run with the same minimal context: Office loads vendored editor modules, styles and assets and uses image/import routes; Call needs a browser secure context, microphone permission and its own service; overlays need accurate geometry and some apps consume shared position/page state. |

[`vite.config.ts`](../../vite.config.ts) emits ES2022, stable filenames and separate modules; HTML/CSS and vendored assets are kept as-is. Generated JS is checked in ([`scripts/build_web.sh`](../../scripts/build_web.sh)), so embedding the current frontend does not require Node. Regenerating/typechecking it needs Node ≥24 and the locked npm toolchain ([`package.json`](../../package.json)).

## Go and the three meanings of WebAssembly here

- **Go activity rules:** [`apps.Activity`, `Session`, `Env`, `Shelf`](../../apps/apps.go) are the real package seam. A caller supplies a viewer list and a send callback; `Session` serializes each activity and issues per-viewer snapshots, timers and directed/broadcast events. `Shelf` accepts opaque per-app bytes; `MemShelf` and a nil or fake `Movie` suffice for selected activities. `Movie` and `Reel` are capabilities, not prerequisites for Polls. [`Chat`](../../chat.go), [`appHost`](../../apphost.go) and the root `Host` remain in `package main`; `NewHost` is not an importable, dependency-free server library. A headless service would need an explicit entry point or a boundary extracted from that package—not a rebranding of `--site`.
- **Server-side WASI:** [`wasm.go`](../../wasm.go) loads modules from the bundle or a checkout's `build/` directory, not from browser assets. Native Go runs them under wazero with WASI preview 1, explicit mounts and stdio, context cancellation, a memory ceiling and the WASM exception-handling feature needed by Pandoc. [`pandoc.go`](../../pandoc.go) converts in a per-import temporary directory; [`datasette.go`](../../datasette.go) uses a persistent CPython module instance with read-only Python files, a single database exposed by a filesystem adapter, and request/response messages over pipes, not a Python HTTP listener. Pandoc is a pinned upstream WASM artifact; Python also needs its matching stdlib and packages. [`build_python.sh`](../../scripts/build_python.sh) names Darwin ARM64 and Linux x86-64/ARM64 as builder targets; that is not evidence of a Linux app release or runtime test. Keep the boxed and unboxed wazero machine-code caches separate. Reuse this layer only for document/SQLite viewing features, and account for redistribution requirements (notably Pandoc's GPL source; see [`licenses/README.md`](../../licenses/README.md)).
- **Host SQLite:** [`store.go`](../../store.go) uses ncruces SQLite, compiled to WASM and translated to Go, without cgo. It is separate from CPython's SQLite and does not depend on `wasmTool`. `party.sqlite` keeps settings, app data and pictures—not guest chat, links, or identities. Matching a `Shelf` is enough for app-state reuse; file interchange would instead need plain and Adiantum-sealed fixtures, old keeper values and checks for platform-specific queue paths. A successful SQLite open is not a verified migration.

## Platform blockers

- **Linux compilation vs desktop parity:** [`native_darwin.go`](../../native_darwin.go) is Objective-C/cgo with Cocoa; it is excluded on Linux. `mac.go` has *no* OS suffix/build tag, and both it and [`main.go`](../../main.go) reference `native*` helpers with no alternate implementation in the checkout. Wails Linux dependencies do not fix these symbols. The pinned Wails v2.17.1 module's `internal/frontend/desktop/linux/window.go` separately declares GTK 3 and WebKitGTK 4.0 by default, or 4.1 with `webkit2_41`. A port has to decide what to implement versus explicitly disable: native menu/responder actions, Dock/file-open, window restoration, notification behavior, and Mac-specific relaunch/erase and update paths ([`party.go`](../../party.go), [`updates.go`](../../updates.go)). `--selftest` bypasses the Wails window at runtime; it does not bypass native references during compilation.
- **Packaging:** [`build_mac_app.sh`](../../scripts/build_mac_app.sh) targets Apple Silicon on macOS 13+, and [`fetch_tools.sh`](../../scripts/fetch_tools.sh) only pins helper binaries for Darwin ARM64. [`docs/release-plan.md`](../../docs/release-plan.md) describes a Mac-only release. Wazero's generated native code is why the signed hardened runtime carries `allow-unsigned-executable-memory` in [`entitlements.plist`](../../packaging/darwin/entitlements.plist). User config/cache lookup already uses Go's `os.UserConfigDir`/`os.UserCacheDir`; bundle resource discovery, update/relaunch, and helper distribution remain separate portability work.
- **Linux listening is not Mac isolation parity:** [`host.go`](../../host.go) selects the separate site only when `h.Sandbox && sandboxing()` is true. On Linux, without `/usr/bin/sandbox-exec`, [`sandbox.go`](../../sandbox.go) returns false and the guest handlers run in the host process. On Mac the child receives the listener and local RPC channels, selected document file descriptors rather than ambient home access, and a canary it must not read ([`site.go`](../../site.go)). `--site` is that child entry point, not an independent daemon command. Retain a tested process/filesystem/network boundary before calling a Linux deployment equivalent for remote guests; WASI confines its own tools, not the rest of the guest service. [`TestTheSiteInItsOwnProcess`](../../sandbox_test.go) and `TestBoxesKeepTheMacOut` are models for testing the isolation property and skip when required facilities are absent.

## Compatibility gates for a follow-up

1. **Rules + one DOM module first.** Use two named viewers, a late arrival and Polls: start, vote/change vote, check each viewer's own selection, close, reopen from a `Shelf`, and confirm persistence retains totals but not per-viewer choices. Exercise mount/update/stop and desktop/narrow layout in a browser, feeding the JSON generated by Go rather than invented fixtures. Reuse [`apps/apps_test.go`](../../apps/apps_test.go), the [Polls rules](../../apps/poll.go) and [`TestCommandsAreTheScripts`](../../apps/fuzz_test.go) as guides. A test here demonstrates reuse without depending on desktop packaging, document tools or the full guest page.
2. **Keep wire compatibility only if existing guests must work unchanged.** Use [`TestAppsOverChat`](../../apps_glue_test.go) as a no-desktop socket fixture and [`TestSocketGraphIsTypes`/`FuzzSocket`](../../graph_test.go) for contract vocabulary and state-walk regression. Assert the real JSON shapes in [`types.ts`](../../web/viewer/types.ts): keyed URL and upgrade, `hello` (initial history, identity, app list and kinds), `apps` open/close, `app` views/events routed by ID, directed payloads kept private, and late-join/reconnect resync. Preserve the distinction between teardown (WebSocket close `1001`, interpreted as session ended) and an interruption that permits reconnect. The graph checks command/type membership, not compatibility of every nested JSON field. Existing guest pages load their scripts from the same host; nothing here proves compatibility with mixed revisions. If independently shipped, add a cross-version fixture or negotiate a version.
3. **Test native parity and optional features separately.** For a replaced desktop bridge, keep the fixture for behavior but smoke-test the real Mac and Linux shell's drop/clipboard/menu events and lock/restart lifecycle. For guest compatibility extend the current headless Chromium walk to Firefox and WebKit and check touch layouts on a real mobile browser; the [testing guide](../../docs/testing.md#what-isnt-covered-yet) explicitly does not claim Safari/Firefox coverage. For optional tools use `TestReadDocument`, `TestDatasetteOnlyReads`/`TestDatasettePages` and `TestPartySealed` ([Pandoc](../../pandoc_test.go), [Datasette](../../datasette_test.go), [store](../../store_test.go)); report skips separately from passes. Keep integration tests on free HTTP/ICE ports, with router mapping, leftover cleanup and tunneling disabled and temporary `HOME` and `XDG_CONFIG_HOME`/`XDG_CACHE_HOME`; see [upstream test precautions](../../CLAUDE.md).

The second result shows that the activity tests also run as **Go `js/wasm` under Node**; it says nothing about the root server as WASM, browser hosting, the WASI tool modules, or whether moving authoritative rules into a guest is appropriate. Neither document-tool artifact was present at its checkout build path; I did not build or run those tools, run the browser walk, or run a desktop build. The Linux runtime security and frontend compatibility statements above are source-based assessments and proposed gates, not passing test claims.
